# 需求/设计阶段体验与开发会话方案（讨论稿）

日期：2026-11-09
状态：**讨论稿，未实施**。对应问题记录：`docs/test-issues-2026-11-09.md` I-05、I-06、I-08、I-09。
目标：解决“不知道当前阶段要做什么、设计缺什么、长开发会话怎么管”的产品体验问题；不改变已确认方向（需求/设计 A、开发 B），不引入批次/证据/Git 门禁。

---

## 1. 现场问题

### 1.1 需求/设计阶段

- 用户不知道“完成需求”之后还需要在设计阶段拆解；AI 在需求阶段又声称已拆解，导致预期错位。
- 设计页无规格时是纯空白，没有“开始拆解”入口和“还缺什么”的提示。
- A-2 未拆解时，设计页没有按需求点展示完成状态；只有类型树，且当批次为空时头部显示空白/“批次规格确认率”。
- 交接包预览当前返回 warnings（例如 FEAT-003 无设计项、无测试用例、1 个开放问题），但 UI 没有把“阻塞错误”和“可接受警告”分开，也没有给出逐项修复入口。
- 需求完成条件只校验卡片；设计完成条件才校验交接包。两个“完成”的含义没有在 UI 上说清。

### 1.2 开发阶段

- 当前一个应用一个 active 开发会话；长任务（30 分钟以上）一直堆在同一会话里。
- 没有会话健康度（时长、消息数、token、上下文压力）提示，也没有“压缩上下文/分阶段新会话”的引导。
- 新建会话会归档当前会话，但没有阶段/目标标签，历史入口也缺失，用户不知道新会话该带什么上下文。
- 交接包已包含 4 个 FEAT、03-PLAN 建议顺序；但开发页没有把它转成可执行的阶段视图。

---

## 2. 设计原则

1. **阶段目标可见**：每个阶段顶部用一句话说明“现在要做什么、完成后得到什么”。
2. **完成条件可操作**：不要只在点击“完成”后报错；提前给出待办清单、阻塞项和修复入口。
3. **只读汇总优先**：先做派生视图（从现有卡片/Spec/交接包计算），不急着加复杂状态机。
4. **AI 建议不自动执行**：开始拆解、分阶段开发、压缩上下文都由用户确认；可提供默认推荐。
5. **开发阶段仍然是原生 build 会话**：不做自定义 dev agent/skill/批次门禁；阶段只是可选的规划与会话组织。
6. **警告 ≠ 阻塞**：未拆解需求点、无测试用例等可作为警告；引用悬空、缺目标/验收等才是阻塞。

## 3. 需求/设计阶段方案

> 2026-11-10 更新：需求阶段确定改为“对话 + 模板化 Markdown 文档”，详见 `docs/plans/2026-11-10-requirements-stage-doc-design.md`。本节 3.2 的“场景树待办”保留为结构化模式/过渡方案；文档模式使用文档章节完整度 + 待澄清列表。

### 3.1 阶段栏与“当前要做什么”

顶部保留 `需求 → 设计 → 开发`，但增加：

- 当前阶段高亮 + 一句提示：
  - 需求：`梳理需求点，确认卡片后进入设计`
  - 设计：`把已确认需求拆成规格，生成交接包后进入开发`
  - 开发：`按交接包实现，用户确认完成`
- 阶段进度摘要：
  - 需求：`需求点 4/4 已确认`
  - 设计：`设计规格 3/4 需求点已拆解 · 交接包 未生成`
  - 开发：`阶段 1/3 · 会话进行中`
- 完成按钮文案与前置检查：
  - “完成需求”前展示：未确认/缺要素的需求点（I-05）。
  - “完成设计”前展示：未拆解需求点、未确认规格、待澄清、交接包阻塞/警告。

### 3.2 需求阶段待办（I-05）

场景树 + 顶部待办：

- 场景行徽标：`待澄清 N`、`待确认 N`、`已完成`（绿色）。
- 需求点行：卡片状态（讨论中/待复核/已确认）+ `待澄清 N` + 缺目标/角色/验收要点提示。
- “需求待办”汇总：
  - 未确认需求点 N
  - 缺目标/角色/验收要点 N
  - 待澄清问题 N（建议不阻塞完成，作为提醒）
  - 点击可跳到对应需求点。
- 指标拆分：`需求卡片确认率` 与 `待澄清 N` 分开显示。

### 3.3 设计阶段待办（新增，I-08 核心）

设计页左侧或顶部增加“设计待办”，按需求点列出：

| 需求点 | 卡片 | 设计状态 | 规格 | 待澄清 | 操作 |
| --- | --- | --- | --- | --- | --- |
| A-1 员工信息维护 | 已确认 | 已拆解 | 实体 1 / 页面 3 / 规则 3，确认率 94% | 1 | 查看/继续 |
| A-2 员工账号关联 | 已确认 | **未拆解** | 0 | 0 | 开始拆解 |
| A-3 组织人员查看 | 已确认 | 已拆解 | 实体 1 / 页面 3 | 0 | 查看/继续 |
| B-1 账号信息维护 | 已确认 | 已拆解 | 实体 1 / 页面 3 | 0 | 查看/继续 |

设计状态定义（派生，不需要新表）：

- **未拆解**：该需求点 Spec 的实体/页面/服务/规则等全部为 0。
- **拆解中**：有设计项，但存在未确认项或待澄清。
- **已拆解**：设计项全部确认且无待澄清。
- **无需拆解**（可选）：用户显式标记“由其他需求点覆盖/本期不做”，需填原因；用于消除 FEAT-003 这类警告。

设计页空状态：

- 文案：`需求已确认，尚未拆解。设计阶段需要把需求点拆成实体、页面、规则等规格。`
- 主按钮：`开始拆解当前需求点`；次按钮：`拆解全部未完成需求点`。
- 按钮动作：向 design agent 发送明确的拆解提示（包含需求点编号、名称、已确认卡片摘要），并展开对话面板。
- 有部分需求点未拆解时，顶部显示 banner：`A-2 员工账号关联 尚未拆解 [开始拆解]`。

设计页头部：

- 把“批次规格确认率”改为“设计规格确认率”；无批次时不显示空白批次名/状态。
- 增加 `需求点视图 / 类型视图` 切换：默认按需求点聚合，展开后按实体/页面/规则分组；保留现有类型树作为另一种视图。

### 3.4 交接包就绪度与“完成设计”

把“生成交接包”和“完成设计”拆成两个明确动作：

1. **生成交接包**（随时可点）：
   - 调用现有 `preview`，展示：
     - 阻塞错误（`issues`）：引用悬空、缺目标/验收等，必须修复。
     - 警告（`warnings`）：未拆解需求点、无测试用例、开放问题，可确认后继续。
     - 覆盖统计：需求点/实体/页面/流程/规则/测试用例。
   - 每个错误/警告带需求点名称和“去处理”链接。
2. **完成设计**（仅当无阻塞错误）：
   - 弹窗展示同样的就绪度清单和“将生成的交接包版本/hash”。
   - 有警告时二次确认：“仍有 1 个需求点未拆解，是否仍然生成并进入开发？”
   - 成功后写盘并解锁开发；失败保留在设计阶段并列出问题。

新增/调整 API（建议）：

- `GET /api/apps/:id/design/status`：返回每个需求点的设计状态、规格计数、确认率、待澄清、缺失类型；以及交接包 readiness（issues/warnings/stats/version/hash）。
- `POST /api/apps/:id/handoff/preview` 已能返回 stats/warnings/files；补充 `issues` 字段（当前阻塞时可能直接抛 400，可统一为 always 200 + issues/warnings）。
- `POST /api/apps/:id/design/skip`（可选）：标记需求点“无需拆解”，记录原因；交接包警告中标注已确认跳过。
- 所有汇总优先服务端计算，前端只展示；避免前端多个 store 计算口径不一致。

### 3.5 阶段切换引导

- 需求完成成功后的弹窗改为：
  - 标题：`需求已完成，进入设计阶段`
  - 说明：`设计阶段需要先把需求拆成规格；不会自动生成。`
  - 按钮：`开始拆解第一个需求点` / `先进入设计看看`。
- 需求阶段禁止生成“进入开发”action；用户说“进入开发”时提示“请先完成需求并进入设计”，或映射为“完成需求并进入设计”。
- 设计阶段完成前，开发阶段保持锁定；锁定原因在点击时说明“请先完成设计并生成交接包”。

### 3.6 验收标准（需求/设计）

- 场景树能显示待澄清/待确认/已完成徽标，切换/确认后实时更新。
- 设计页能按需求点显示未拆解/拆解中/已拆解，A-2 这类缺口一眼可见。
- 空设计页有“开始拆解”入口，点击后 design agent 收到明确提示。
- 生成交接包前能看到阻塞错误 vs 警告；有警告时可确认继续。
- 需求完成/设计完成弹窗都说明“完成条件”和“下一步”。
- 不再出现“批次规格确认率/空批次名”等旧概念。
- 无新增批次/证据/Git 门禁。

## 4. 开发阶段会话方案

### 4.1 现状与事实

- 一个应用一个 active 开发会话；`app_sessions` 记录 opencode sessionID；`{new:true}` 归档旧会话。
- 开发页只显示当前 active 会话；归档会话无入口。
- opencode 2.2.5 原生支持 `POST /api/session/{id}/compact`（durable compaction，在下一个 step boundary 执行）。
- 当前模型 deepseek-flash 上下文上限约 1M token；30 分钟会话不一定爆上下文，但消息/成本/焦点会持续增加。
- 交接包已有 `03-PLAN.md` 建议顺序和按 FEAT 的实施清单。

### 4.2 方案对比

| 方案 | 做法 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| A. 单会话 + 压缩 | 保持一个会话；达到阈值时调用原生 compact；显示会话健康度 | 改动小；上下文连续；不新增阶段模型 | 压缩可能丢细节；大项目仍是一个长会话 | **默认** |
| B. 分阶段会话 | 交接包生成时派生阶段；每个阶段一个会话；阶段完成归档 | 上下文 bounded；进度清晰；易恢复 | 需要阶段数据/UI；跨阶段上下文需摘要；阶段划分可能不准 | **可选** |
| C. 混合（推荐） | 默认单会话 + compact；交接包较大时提供“分阶段开发”选项；阶段会话带 phase brief | 兼顾连续性与可控性；不强制 | 实现量中等；需要阈值与摘要策略 | **推荐** |

### 4.3 推荐方案：单会话默认 + 可选分阶段

#### 4.3.1 会话健康度

开发页顶部显示：

- 会话时长、消息数、工具调用数、token 使用（若 opencode 返回）。
- 阈值提示：
  - 时长 > 30 分钟 或 消息 > 100 条 或 token > 60% 上下文：显示“建议压缩上下文或开启新阶段会话”。
  - 不自动中断，只提示。
- 按钮：
  - `压缩上下文` → `POST /api/session/{id}/compact`，时间线显示 compaction 事件。
  - `新建阶段会话`（见下）。

> **落地记录（2026-11-11，I-09a 已完成）**：
>
> - 阈值**只按模型上下文百分比**：≥60% 黄“建议压缩”、≥85% 红“强烈建议”；**不设**时长/消息/工具阈值（只展示，不提示）。
> - 上下文用量：`DevProgress.context = { used, limit, percent, level }`。`used` 取**最新一条 assistant** 消息的 `input + cache.read + cache.write`（无则 0）；**不用**会话聚合 `info.tokens`（那是累计值，会超 100%）。`limit` 取 `GET /api/model` 的 `limit.context`（按 `provider/model + directory` 缓存 60s；查不到为 null → `percent=null, level='unknown'`）。
> - 开发页顶部：`上下文 62% (65k / 1.05M)` chip（ok 灰 / warn 黄 / danger 红）；limit 缺失显示 `上下文 65k`；无数据 `上下文 —`；tooltip 标注“约（按最新一轮 assistant 消息估算）”。
> - warn/danger：时间线上方提示条 + `压缩上下文` 按钮（仅 active 非只读；只读会话 chip 仍显示，不显示按钮/提示条）。
> - 右侧“会话”卡：时长、消息数、工具数（含失败）、上下文（`62% · 65k / 1.05M`）、Token 总量。
> - `npm run smoke:dev-health`（真实 opencode）+ 单测 + Playwright 覆盖；详见 `docs/STATUS.md`「I-09a 完成」。分阶段 I-09b-1（U6）已实施（2026-11-12）；U7-1 后端已实施（2026-11-12，`smoke:dev-phases`），U7-2 前端已实施并评审（2026-11-12；见「U7-2 完成」）。

#### 4.3.2 交接包规模识别与建议分阶段（I-09b-1，2026-11-12 定稿，已实施）

> 状态：**U6 已实施**（`backend/src/handoff/design-scale.ts`、`manifest.scale`、`04-PLAN.md`「0. 建议分阶段开发」、README/弹窗/开发页提示）；**U7-1 后端已实施**（2026-11-12：`manifest.phases` + `app_dev_phases` + 阶段 API/brief/摘要，`smoke:dev-phases`），**U7-2 前端已实施并评审**（2026-11-12：入口/阶段条/弹窗/完成-跳过-重新打开/会话 chip/只读 + 主会话并发刷新修复）。验证详见 `docs/STATUS.md`「I-09b-1 完成」「U7-1 完成」「U7-2 完成」与 `docs/plans/2026-11-12-i09b1-implementation-brief.md` §8、`docs/plans/2026-11-12-u7-1-implementation-brief.md` §8、`docs/plans/2026-11-12-u7-2-implementation-brief.md` §8。

> 名称纠偏：当前交接包文件是 **`04-PLAN.md`**（00-README / 01-REQUIREMENTS / 02-DATA-MODEL / 03-PAGES / 04-PLAN / 05-CHANGES），不再使用旧的 “03-PLAN / FEAT” 口径；需求结构是 Scene / Epic / Story。

**范围**：只做 U6——确定性规模识别 + `04-PLAN.md` 建议分阶段 + `00-README.md` 提示 + 交接包弹窗/开发页提示。**不做**阶段模型、一阶段一会话、phase brief（U7 预设计见 4.3.3，本轮不实施）。

**规模统计（确定性，不调模型）**：

- `counts`：`scenes / epics / stories / entities / fields / relations / pageSets / pages / prototypes`。
- `textBytes`：`00—05 + schema.sql + prototype-template.json` 的 UTF-8 字节和；**不含** `manifest.json`、PNG、HTML，也不含本建议章节自身（按建议章节渲染前的文本计算，避免循环）。
- **触发阈值（任一命中）**：
  - `stories >= 10`
  - `pages >= 12`
  - `textBytes >= 102400`（100KB）
- 阈值常量集中定义（如 `HANDOFF_SCALE_THRESHOLDS`），便于后续调整；`manifest.json` 记录实际计数、阈值与命中项，UI 展示真实数字，不只给结论。

**产出**：

- `manifest.json` 增加 `scale`：`level(normal|large) / suggested / counts / textBytes / thresholds / triggers / phaseCount / derivedFrom`。
- `04-PLAN.md` 命中时在最前面增加 `## 0. 建议分阶段开发（可选）`：
  - 说明规模与命中阈值；
  - 阶段草案；
  - 明确“只是建议、不强制、不做门禁；仍可单会话完成”。
- `00-README.md` 命中时增加一句“本交接包较大，建议按 `04-PLAN.md` 的《建议分阶段开发》推进；也可单会话完成”。
- 设计交接包弹窗/开发页显示“规模：N Story / M 页面 / X KB”与“建议分阶段”提示，能跳转到 `04-PLAN.md`。
- `preview` 与 `generate` 使用同一套计算；`preview` 不写盘。

**阶段草案派生（确定性）**：

- 固定第一阶段：`数据模型与基础框架`（02-DATA-MODEL / schema / App Shell / 导航 / 公共组件）。
- 有 Epic 时：每个 Epic 一个阶段（按需求文档顺序），范围 = 该 Epic 的 Story + 绑定该 Epic 的页面集/页面；Epic 无页面集时注明“按 Story 实现接口/后端能力”。
- 无 Epic 归类的页面集：放到最后的 `其他页面与收尾`。
- 完全没有 Epic 时：按页面集顺序每 2—3 个一组派生阶段；无页面集时只给一个“全量实现”阶段。
- 不在 U6 做阶段状态、会话绑定或自动摘要；草案只写进 `04-PLAN.md`。

#### 4.3.3 阶段模型（U7 定稿，2026-11-12）

> 状态：**U7-1 后端已实施并评审；U7-2 前端已实施并评审（2026-11-12）；U7-3 真实模型全链路已验证（2026-11-12：model + fallback + P2）**。详细设计见 `docs/plans/2026-11-12-u7-phased-development-design.md`；本节只保留摘要。

用户可见叫“开发阶段/里程碑”，不叫批次，不做门禁：

- **按需生成**：U6 判定 large 后，开发页提供“按阶段开发”；用户点击才写入 `app_dev_phases`。
- 阶段来源与 `04-PLAN` 一致：基础 + 每 Epic 一阶段 + 其他页面。
- 新表 `app_dev_phases`（`app_id/change_set_id/handoff_version/phase_key/title/goal/scope_json/status/summary/summary_source/ord/timestamps`）+ `app_sessions.dev_phase_id`；阶段 ID 全局唯一。
- 一阶段一会话（可多会话但同一时间只有一个 active）；阶段完成**不归档**，开始下一阶段时才归档当前 active。
- 阶段完成时用 `generateText` 生成 5—10 行摘要（失败回退最后 assistant 文本）；下一阶段 brief 使用上一阶段摘要。
- 阶段状态：未开始/进行中/已完成/跳过；向已完成/已跳过阶段会话发消息自动回到进行中；不影响 `apps.status`/`/complete`。
- 会话列表保持按变更单分组，会话项加阶段 chip；阶段全部完成只提示，不自动完成。
- 新变更单/新交接包重新生成阶段；旧阶段保留历史；不做阶段级取消。

#### 4.3.4 左侧会话列表（Codex 风格，I-10）

当前：一个应用只显示一个 active 开发会话；点“新会话”会归档旧会话，弹窗明确说“旧会话暂不在界面中展示”。用户希望像 Codex 左侧项目会话列表一样，能看到该应用的全部开发会话，并可在超长项目中用多个会话推进。

建议：

- **布局**：开发页左侧增加可折叠会话栏（约 260px），与中间时间线、右侧会话信息并列；窄屏可收起为图标。
  - 顶部：`开发会话` + `新会话` 按钮 + 搜索框。
  - 列表项：会话标题（可重命名）、最后一条消息摘要、时间、模型、状态（进行中/已完成/已归档）、消息数/工具数（可选）。
  - 分组：今天 / 昨天 / 更早；接入 I-09 分阶段后可按阶段分组。
  - 当前 active 会话高亮；hover 提供“重命名 / 归档 / 恢复”。
  - 点击已归档会话：只读查看完整时间线；点“恢复为当前会话”后才可继续发送/停止。
- **多会话语义**：
  - 仍保持“同一时间只有一个 active 会话”用于 prompt/SSE/权限/表单，避免并发写同一工作目录。
  - 归档会话保留在 opencode 与 `app_sessions`，不再从前端消失。
  - 新会话创建时提示改为：`当前会话会归档，新会话不会自动接续旧上下文；旧会话保留在左侧列表，可随时查看/恢复。`
- **数据与 API**：
  - `app_sessions` 已有多行（active/archived/stale）与 `opencode_session_id`，无需重建表；可补 `title`、`last_message_at`、`message_count` 缓存列（可选）。
  - `GET /api/apps/:id/development/sessions`：合并 `app_sessions` 与 opencode 会话信息（标题、时间、模型、状态、消息数、费用/token），按时间倒序。
  - `POST /api/apps/:id/development/sessions/:sid/activate`：切换 active（归档当前、激活目标；需校验 opencode 会话仍存在）。
  - `PATCH .../sessions/:sid`：重命名/备注；`DELETE .../sessions/:sid`：归档（不删除 opencode 数据，除非用户确认）。
  - `GET .../development?sessionId=`：读取指定会话的只读时间线；默认 active。
  - SSE 仍按 active opencode sessionID 过滤；切换会话后重连。
- **会话标题**：默认用首条用户消息摘要或 `应用名 · 日期`；支持用户重命名；opencode 自动标题可作初始值。
- **与分阶段的关系**：会话列表是基础能力，先于阶段模型；阶段只是给会话加 `phaseKey/phaseTitle` 标签并自动写 phase brief。
- **与 Codex 的差异**：Codex 按项目分组；工作台的应用本身就是项目，所以会话列表按应用展示即可，不需要跨应用混排。

> 这张图里还有 43m55s、257 个工具、115k/180k token 的真实长会话，正说明“会话健康度 + 会话列表 + 可选分阶段”是必要的。

**落地记录（2026-11-11，I-10 已完成）**：

- 开发页左侧 260px 会话栏（<1100px 默认折叠/覆盖层），中间时间线、右侧会话信息/交接文档/文件变化。
- 列表按**变更单**分组（seq 倒序：`初始开发` / `变更 #N · 标题` / `早期会话`），组头显示状态 + `交接包 vZ` + 数量；默认展开 active 组；支持标题/备注搜索。
- 列表项标题/时间/模型/状态/handoff 版本；active 高亮；hover 重命名/归档/恢复。
- 归档会话只读查看（Composer 替换为只读横幅 + 恢复按钮；权限/表单禁用；停止隐藏）；恢复时若 handoff 版本不同先提示“建议新建会话”。

#### 4.3.5 压缩与摘要

- 优先使用 opencode 原生 compact，不自研摘要。
- 若阶段会话需要承接上一阶段：用上一阶段最后一条 assistant 总结 + 用户填写的“阶段交接说明”生成 phase brief；不强制模型再总结。
- 可选：阶段完成时用 `generateText` 生成 5—10 行摘要，写入阶段记录；成本可控，但增加一次模型调用。

> **落地记录（2026-11-11，I-09a 已完成）**：
>
> - 用 opencode 原生 `POST /api/session/{id}/compact`（body `{}`），工作台不自研摘要；用户手动触发，不自动。
> - API：`POST /api/apps/:id/development/compact` → `assertDevReady` + active 会话（无 active 409「当前没有进行中的开发会话」）→ 事件 `context-compacted` → `{ ok:true, message:'已请求压缩上下文，将在下一步生效' }`；opencode 错误按可读信息透传（不裸抛 500）。
> - **实测（opencode 2.2.5）**：compact 写入一条 `type:'compaction'` 消息（`status`/`reason`/`error`）；空会话时 HTTP 仍 200，但消息 `status:'failed'` + `error.message:'Nothing to compact yet'`。因此时间线按 status 区分：
>   - 成功 → `kind:'compaction'`，文本“上下文已压缩”；
>   - 失败 → `kind:'compaction-failed'`，文本“上下文压缩未执行：<原因>”（`Nothing to compact yet` 映射为“没有可压缩的上下文”）。
> - 时间线渲染为轻量系统提示（不当作 assistant 文本）；压缩后健康度需等新一轮 assistant 消息才回落（不强制即时变化）。
> - 前端二次确认文案：“压缩会用总结替换较早上下文，可能丢失细节；当前会话与代码不会中断。继续？”；成功提示“已请求压缩，将在下一步生效”。
> - 验证：`smoke:dev-health`（真实 opencode，不调用模型）、后端单测（compaction 归一化/failed）、Playwright（chip/提示条/按钮/只读）；详见 `docs/STATUS.md`「I-09a 完成」。阶段会话（I-09b）未做。

## 6. 待讨论问题

1. **待澄清是否阻塞完成需求/设计？**
   - 建议：不阻塞，作为提醒；当前后端也不阻塞。若你希望硬阻塞，需要同步改完成校验与文案。
2. **未拆解需求点是否阻塞完成设计？**
   - 建议：警告 + 二次确认，不硬阻塞（当前交接包校验也只给 warning）。是否要允许“无需拆解”标记？
3. **设计页默认视图**：按需求点聚合，还是保留按类型树？
   - 建议：默认按需求点（更符合“还缺哪个点”），保留类型视图切换。
4. **开发默认模式**：单会话 + compact，还是默认按阶段？
   - **已决策（2026-11-12）**：默认单会话 + compact；大交接包只给“建议分阶段”，不强制（U6）。
5. **分阶段阈值**：旧 FEAT > 4 / 设计项 > 40 / 交接包 > 80KB 是否合适？
   - **已决策（2026-11-12）**：改用当前模型口径——Story ≥10 或 页面 ≥12 或 交接包文本 ≥100KB；同时展示实际计数。
6. **阶段完成是否归档会话？**
   - **暂缓（U7）**：预设计为由用户点“阶段完成”，不强制归档；进入下一阶段新建会话时再归档旧会话。
7. **是否把阶段数据落表**：轻量 settings 还是 `app_dev_phases`？
   - **暂缓（U7）**：初步倾向新表 `app_dev_phases`（绑定变更单/交接包版本）；需真实数据后定稿。
8. **会话列表默认形态**：默认展开还是折叠？按日期分组还是按阶段分组？
   - 建议：默认展开；未接入阶段前按日期分组，接入阶段后可按阶段分组切换。
9. **归档会话的权限**：只读查看，还是允许“恢复为当前会话”后继续？
   - 建议：允许恢复，但同一时间只保留一个 active 会话，避免并发写同一目录。
10. **会话标题**：默认用首条用户消息摘要、opencode 自动标题，还是 `应用名 · 日期`？
   - 建议：优先 opencode 自动标题，空则用首条用户消息摘要；支持手动重命名。

## 7. 与现有方向的一致性

- 需求/设计仍是 A 方案；设计拆解仍由 design agent + 结构化协议完成。
- 开发仍是 B 方案：原生 `build` agent + 原生会话/权限/表单/取消。
- 不新增批次、证据、Git、测试门禁。
- “开发阶段”只是可选的规划/会话组织，不是审批流；用户可始终使用单会话。
- 所有汇总只读派生，不改变已确认 Spec/交接包的确定性渲染。
