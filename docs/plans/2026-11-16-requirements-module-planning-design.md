## 1. 问题

当前需求 AI 生成是**按当前模块**的：
- prompt 只注入当前模块的模板/文档/Epics（`backend/src/chat/doc-prompt.ts`）；
- `<<<DOC_JSON>>>` 只返回一份文档；
- 新应用默认模块标题=应用名（`MOD-001`），于是 AI 把整个系统写进“订单管理系统”一份 PRD；
- 模块树只是容器，内容没有模块划分。

用户样例：创建 app1 后输入“订单管理系统，含商品/商品明细 CRUD、订单管理（选商品生成订单、不支付）、订单-商品一对多、商品-明细一对一”，AI 只生成了“订单管理系统”一个模块的一份文档；期望是 **商品管理** + **订单管理** 两个模块，并分别生成完整 PRD。

### 2.1 确认边界（2026-11-16 第二轮确认）

- **需求阶段、最终确认之前**：可以随时 AI 重新规划；部分模块已确认时，按 §5.3 自动重开 + 明确警告。
- **用户点击最终“完成需求阶段”（应用级需求确认/bundle confirm）后**：当前版本需求视为已确认，**模块结构与已确认需求锁定**。
  - 设计阶段：不允许直接新增/修改/归档模块或修改已确认需求；要变更就按现有流程**发起 Change Set（需求+设计）**。
  - 开发/完成阶段：同样走 Change Set。
  - 直接的“AI 规划模块”入口在设计/开发阶段禁用，并提示使用 Change Set/重新编辑需求。
- **Change Set 内的 AI 重新规划**（在变更范围内改模块边界/新增/替换模块）不在 RMP-1/RMP-2 范围；需另行设计（M5 目前禁止变更中归档、范围固定）。现有 Change Set 的模块选择/新增模块语义不变。
- 现有“重新编辑需求”入口行为不变；但按用户决策，设计/开发的正式变更优先走 Change Set。

## 3. 语义定义

- **模块**：业务域/子域，是需求、设计、开发、协作的共同边界。一个模块拥有：
  - 一份完整模板 PRD（13 节或 6 节，取决于应用模板）；
  - 一组实体/页面集/页面（设计阶段）；
  - 独立版本、确认状态、负责人、变更范围。
- **场景（Scene）/ Epic / Story**：模块**内部**的拆分。一个模块可以包含多个场景/Epic。
  - 例：商品管理 → Epic「商品档案」「商品明细」；订单管理 → Epic「订单创建」「订单查询」。
- **跨模块关系**：需求阶段只做说明与依赖提示；设计阶段用跨模块实体关系/FK 表达（M4/M6 已允许，warning 不阻塞）。
  - 例：订单管理 → 商品管理（订单引用商品，N:1）；商品与明细 1:1 在商品管理内部。
- **拆分规则（AI prompt 必须写死）**：
  - 按业务域/职责边界拆，不按“列表/新增/修改/删除”拆，不按单个实体拆；
  - 同一业务域的实体与其明细归同一模块（商品 + 商品明细 → 商品管理）；
  - 明确排除项（如“不做支付”）不生成模块；
  - 模块数量由内容决定；通常 1—6 个，不设硬上限；过多时给 warning 与生成时长提示。

## 4. 目标流程

### 4.1 新应用首次：自动模块规划 → 确认 → 逐模块生成

```text
用户创建应用（默认模块 MOD-001=应用名，空文档）
  ↓
用户第一条实质需求（默认模块空）
  ↓
AI 只返回“模块拆分建议”（MODULE_PLAN_JSON），不直接写文档
  ↓
聊天中展示「模块拆分建议」卡：模块名/说明/范围/建议 Epics/依赖/覆盖与缺口
  ↓
用户可编辑名称、说明、范围、增删模块、调整顺序
  ↓
[应用拆分并生成] ───────────────┐
  ↓                              │
结构应用：复用 MOD-001 + 新建模块  │
  ↓                              │
逐模块生成完整 PRD（SSE 进度）    │
  ↓                              │
每模块 draft，用户逐模块审阅/确认  │
                                 │
[保持单模块] ────────────────────┘
  ↓
按现有单模块流程生成 MOD-001
```

- **不自动创建模块**：建议卡必须由用户确认后才写库。
- **不自动确认文档**：生成后是 draft，仍走模块确认 → `完成需求阶段`。
- 若 AI 判断只有一个业务域：建议卡只有 1 个模块；用户可直接应用（复用默认模块）或保持单模块。
- 若规划失败/JSON 非法：展示错误与重试；提供“保持单模块”兜底，不静默建错模块。

### 4.2 随时重新规划（关键新增）

入口（建议）：
- 需求大纲/需求总览中的 **“AI 规划模块”** 按钮；
- 弹窗内可填写调整指令（默认：“请根据当前全部需求内容重新拆分模块”），例如“把订单拆成订单和售后”“把商品明细并入商品管理”“按业务域重新划分”；
- 首次建议卡也提供“重新规划”入口。

流程：
```text
读取当前全部未归档模块的文档/Epics/Story + 模块规划
  ↓
AI 返回新的模块划分建议（含 保留/改名/新建/合并/拆分/归档 建议 + 覆盖/缺口）
  ↓
预览 diff（当前模块 → 新模块；哪些保留、哪些归档、哪些重新生成）
  ↓
用户调整后确认
  ↓
结构应用（保留/改名/新建/归档）+ 按需生成新/变更模块
  ↓
旧模块归档保留（内容/版本/对话不丢，可恢复）
```

原则：
- **重结构、轻搬运**：结构变化（合并/拆分/重划边界）不直接把章节/Epic 从旧文档剪切到新文档；新/变更模块按“当前全部需求”重新生成完整 PRD，旧模块归档留档。
- **未变模块保留**：业务域与范围未变的模块保留原 ID/文档/版本/对话，不重生成（可手动选择重新生成）。
- **改名**：保留 ID/文档/版本/对话，更新模块标题与文档标题。
- **归档**：旧模块归档而非删除；内容/版本/对话保留，可恢复。
- **已确认模块**：重新拆分会改变结构，必须显式提示并重新打开（退回 draft、清确认）；详见 §5.3。

### 4.3 设计/开发阶段边界

- **需求阶段（最终“完成需求阶段”之前）**：随时可以 AI 重新规划；包括已有内容、部分模块已确认（需警告 + 重开）。
- **用户点击最终“完成需求阶段”后**：模块结构与已确认需求锁定。
  - 设计阶段：不允许直接修改模块/已确认需求；走现有 **Change Set（需求+设计）**。
  - 开发/完成阶段：同样走 Change Set（M5 模块选择），不直接重规划。
  - “AI 规划模块”入口在设计/开发阶段禁用并提示路径。
- **Change Set 内 AI 重新规划**不在 RMP-1/RMP-2 范围（见 §2.1），需另行设计；现有 Change Set 语义不变。
- 本设计不改变现有阶段门禁与 Change Set 语义。

## 5. 重新拆分的内容策略（**待用户确认的关键点**）

### 5.1 为什么不做“章节/Epic 搬运”

每个模块是**完整 PRD**（模板所有章节）。把某个章节/Epic 从模块 A 剪切到 B：
- A/B 都会出现缺章节/半成品，需要补写；
- 手动编辑、版本、对话、确认状态难以按章节拆分；
- 合并/拆分时冲突与丢失风险高。

因此结构变化采用 **重新生成 + 旧模块归档**，而不是机械搬运。

### 5.2 建议的映射动作

AI 建议 + 用户在预览中确认，每个建议模块带一个动作：

| 动作 | 条件 | 处理 |
| --- | --- | --- |
| `keep` | 业务域/范围未变 | 保留原模块 ID/文档/版本/对话，不改内容 |
| `rename` | 仅名称/描述变化 | 保留 ID/文档/版本/对话，更新标题与文档标题 |
| `regenerate` | 范围变化/用户要求 | 保留或新建模块 ID；按新范围重新生成完整 PRD（新 `ai` 版本），旧内容仍在历史版本 |
| `create` | 新业务域 | 新建模块（空文档）→ 生成完整 PRD |
| `archive` | 旧模块被替换/合并/删除 | 归档（不删除），内容/版本/对话保留，可恢复 |

- 未匹配的旧模块默认 `archive`；预览中明确列出。
- `keep/rename` 不触发生成；`regenerate/create` 进入生成队列。
- 合并：新模块 `create` 或 `regenerate`，来源旧模块 `archive`；新文档由 AI 基于旧模块全部需求生成。
- 拆分：新模块 `create`（每个拆分目标），旧模块 `archive` 或 `regenerate`（若保留其中一个）。

### 5.3 已确认模块/应用级确认

- 若任一未归档模块已确认，重新规划预览顶部提示：
  “本次调整会重新打开已确认模块（退回草稿），应用级需求确认/聚合版本需重新完成。”
- 用户确认后：
  - 受影响的 `keep/rename` 模块若仅改名：确认状态可保留？**建议**：仅改名不动内容可保留确认；但结构变化通常伴随范围变化，保守做法是重开。
  - `regenerate/create/archive` 涉及结构：相关模块退回 draft，清 `confirmed_at`；清应用级需求确认（如已置位）；bundle 需重新确认。
- 若用户已点击最终“完成需求阶段”（app 进入 design）：不允许直接重规划；按现有流程走 **Change Set（需求+设计）**（设计/开发阶段提示同路径）。
- 已确认决策（2026-11-16）：需求阶段、最终确认之前，已确认模块采用 **自动重开 + 明确警告 + 需再次确认**；最终确认之后结构锁定，走 Change Set。

### 5.4 旧内容如何保留

- 归档模块保留：文档、章节、版本、对话、确认记录（如有）、设计输入（如设计阶段曾生成；本流程仅需求阶段）。
- 新生成模块的 prompt 会输入“当前全部需求内容”（旧模块文档/Epics/Story 的聚合摘要），尽量保留业务信息，但不保证逐字复制；用户需审阅新文档。
- 预览明确写：“旧模块归档保留，可恢复；新模块文档为重新生成，请逐模块审阅。”

## 6. 模块规划输出（`MODULE_PLAN_JSON`）

新增协议分隔符：`<<<MODULE_PLAN_JSON>>>`（与 `DOC_JSON` / `DESIGN_JSON` 并列，互不复用）。

建议结构：

```jsonc
{
  "kind": "initial",                  // initial | replan
  "modules": [
    {
      "key": "product",               // AI 临时 key，仅用于依赖/覆盖引用
      "title": "商品管理",
      "description": "商品与商品明细的档案维护",
      "scope": ["商品档案 CRUD", "商品明细 CRUD", "商品与明细 1:1"],
      "suggestedEpics": [
        { "title": "商品档案", "stories": ["商品列表", "新增商品", "修改商品", "删除商品"] },
        { "title": "商品明细", "stories": ["明细列表", "新增明细", "修改明细", "删除明细"] }
      ],
      "existingModuleId": null,       // replan 时 AI 可建议匹配；后端校验
      "action": "create"              // create | keep | rename | regenerate
    },
    {
      "key": "order",
      "title": "订单管理",
      "description": "选择商品生成订单，不做支付",
      "scope": ["订单创建", "订单查询", "订单状态（待确认）"],
      "suggestedEpics": [
        { "title": "订单创建", "stories": ["选择商品生成订单", "订单列表/详情"] }
      ],
      "existingModuleId": null,
      "action": "create"
    }
  ],
  "dependencies": [
    { "from": "order", "to": "product", "description": "订单引用商品，N:1；订单模块不重复建商品实体" }
  ],
  "coverage": [
    { "requirement": "商品 CRUD", "moduleKey": "product" },
    { "requirement": "商品明细 CRUD", "moduleKey": "product" },
    { "requirement": "订单创建/查询", "moduleKey": "order" }
  ],
  "unassigned": [
    { "requirement": "订单状态流转", "reason": "需求未明确状态机，已作为待确认" }
  ],
  "openIssues": ["订单是否需要库存扣减？", "商品/明细删除是否受订单引用限制？"],
  "warnings": ["未发现支付模块（符合“不做支付”）"]
}
```

规则：
- `modules` 至少 1 个；标题非空、唯一；不设硬上限（技术保护可设 50）。
- `title` 用业务域名词（商品管理/订单管理），不要“商品列表模块”“新增商品模块”。
- `scope` 说明边界与排除项；`suggestedEpics` 用于预览，不直接写库。
- `coverage/unassigned` 让用户看到需求是否被完整覆盖；`unassigned` 不阻塞应用，但显示 warning。
- `existingModuleId` 只允许 replan；必须是当前未归档模块 ID；`action` 与 ID 一致性由后端校验。
- 首次规划 `kind=initial`，所有 `action=create`（第一个模块复用默认模块）。
- 规划失败/非法 JSON：不写库；前端显示错误 + 重试 + “保持单模块”。

## 7. 逐模块生成

### 7.1 生成输入

每个模块生成完整 PRD，prompt 包含：
- 应用信息、所选需求模板（全部章节/必填/guidance）；
- 原始需求（首次对话或当前全部需求聚合）；
- 模块规划（全部模块标题/范围/依赖/覆盖）；
- **当前模块**的范围、out-of-scope、建议 Epics；
- 其它模块的边界（避免重复），跨模块依赖；
- 输出协议：沿用 `<<<DOC_JSON>>>`，要求：
  - 只写当前模块；不生成其它模块的需求；
  - 完整覆盖模板章节；required 章节不能空；不适用处写“本模块不涉及/不适用”并说明；
  - Scene/Epic/Story 只属于当前模块；省略 ID（后端分配全局 ID）；每个 Epic 至少 1 Story；
  - 跨模块关系写在约束/数据相关章节，不重复建实体；
  - 不做支付等排除项不得出现为功能；
  - 信息不足写 `> 待确认：...`。
- 生成使用需求阶段模型/agent；独立生成入口，**不写入模块对话历史**（避免污染）；失败可重试。

### 7.2 生成与版本

- 结构应用时创建/复用模块：新模块空文档 v1（现有 `createModule` 行为）。
- 生成成功后应用 DOC_JSON：
  - 写章节/结构化数据；产 `source='ai'`（或新增 `initial`，建议复用 `ai` 并带 `changeSetId=null`）版本；
  - 不自动确认；
  - 失败保留空/部分文档，标记失败，可重试。
- `keep/rename` 模块不生成；`regenerate` 生成新版本，旧版本保留可回滚。

### 7.3 进度、失败、重试

- 逐模块**顺序**生成（避免并发限流/上下文竞争），SSE 推送：
  - `plan`（结构应用结果：created/kept/renamed/archived/reopened）；
  - `module-start` / `module-progress`（可选 token/阶段）/ `module-done` / `module-error`；
  - `all-done`。
- UI 显示每模块状态（等待/生成中/成功/失败/跳过），支持：
  - 重试失败模块；
  - 取消剩余生成（已完成的保留）；
  - 模块多时显示预计时长；不设硬上限，但 >8 个给 warning。
- 生成中允许查看已完成模块；暂不允许再次重规划/结构变更，直到完成或取消。

## 8. 默认模块、ID、标题、对话

- 首次规划应用时：**第一个建议模块复用空默认模块 `MOD-001`**：
  - 更新 `app_modules.title/description`；
  - 更新该模块文档标题为 `${appName} · ${module.title} 需求文档`（当前 `docTitleFor` 对 MOD-001 特例是 `${appName} 需求文档`，需要显式覆盖/调整，保证新语义）；
  - 保留 ID、文档、版本、对话（初始需求对话留在该模块）；
  - 其余模块新建 `MOD-002...`，按规划顺序。
- 若默认模块已有内容：首次自动规划不再触发（正常模块内对话）；用户可用“AI 规划模块”重新规划（见 §5）。
- 若默认模块为空但用户选择“保持单模块”：按现有流程生成 MOD-001，不新建。
- Replan：
  - `keep/rename` 保留原 ID/对话；
  - `create` 新 ID；
  - `archive` 旧模块保留对话，归档只读；
  - 不新建设计项目/交接包（需求阶段）。
- 模块 key 全局唯一；规划顺序 = position 顺序。

## 9. UI/交互

### 9.1 首次建议卡（聊天内）

- 位置：默认模块聊天中，AI 回复后。
- 内容：
  - 标题“模块拆分建议”；
  - 模块列表（可编辑标题/说明/范围；上移下移；删除/新增）；
  - 建议 Epics（可折叠）；
  - 依赖与覆盖/缺口/warnings/openIssues；
  - 按钮：`应用拆分并生成`、`保持单模块`、`重新规划`。

- 刷新/重进：建议卡应可恢复（持久化草稿），未应用可继续；已应用显示结果。

### 9.2 随时重规划（弹窗）

- 入口：需求大纲头部/需求总览 `AI 规划模块`（仅需求阶段）。
- 弹窗：
  - 当前模块概览（标题/范围/状态/确认）；
  - 指令输入（默认“根据当前全部需求内容重新拆分模块”）；
  - `生成建议` → 预览 diff；

- 设计/开发阶段入口禁用并提示路径（重新编辑需求 / 发起变更）。

### 9.3 进度

- 组件展示模块列表与状态、当前生成模块、失败原因、重试/取消；
- 生成完成后刷新大纲/模块列表，切到第一个生成模块；
- 失败模块在大纲中标记“生成失败”，可重试；
- 生成中不阻塞查看已完成模块。

## 10. API / 数据 / 持久化（建议）

### 10.1 规划预览

`POST /api/apps/:id/requirements-modules/plan/preview`

body：
```jsonc
{
  "kind": "initial" | "replan",
  "instruction": "可选的调整指令",
  "message": "首次需求的用户消息（initial 时）",
  "persistChat": true
}
```
- 只读（不创建模块/文档/版本）；调用需求阶段模型生成 `MODULE_PLAN_JSON`；
- 返回 `{ plan, basis: { modules, bundleVersion, docHashes }, warnings }`；
- initial 时把用户消息 + 规划回复写入默认模块 chat 历史（可选，建议），保证刷新可见；
- 规划草稿持久化（建议 settings key `app.<id>.modulePlanDraft`，含 plan JSON/base 版本/时间；应用/丢弃后清理）；不新建表。

### 10.2 结构应用

`POST /api/apps/:id/requirements-modules/plan/apply`

body：`{ plan, planDraftId? }`
- 校验 plan（模块标题/动作/ID/覆盖）；
- 事务：复用/改名/归档/新建/重开；同步默认模块标题/文档标题；清理/更新 bundle 确认状态；
- 返回 `{ modules, created, kept, renamed, archived, reopened, generation: [{moduleId, action}] }`；
- 不生成文档（生成单独入口，便于重试）。

### 10.3 逐模块生成

`POST /api/apps/:id/requirements-modules/generate`（SSE）

body：`{ moduleIds?: string[], reason: 'initial' | 'replan' | 'retry' }`
- 默认生成 `generation` 列表中的 `create/regenerate` 模块；
- 逐模块生成、应用 DOC_JSON、事件进度；
- `moduleIds` 用于失败重试；
- 字段/权限沿用现有模块守卫；已归档模块 409；非需求阶段 409。

### 10.4 数据

- 不新增表（建议）：模块/文档/版本/对话已有；规划草稿用 settings key。
- 若后续需要规划历史/审计，再评估 `app_requirement_module_plans` 表。
- `MODULE_PLAN_JSON` 消息/草稿不进入 DOC_JSON 解析；互不干扰。

## 11. 校验、边界、错误

- 规划：
  - 1—N 模块；标题非空/唯一；不按 CRUD/实体拆（prompt + 关键词 warning）；
  - `existingModuleId` 必须属于当前应用且未归档；`action` 与 ID 一致；
  - 覆盖：未分配需求 warning；不阻塞；
  - 规划 JSON 非法/模型失败：不写库，返回可读错误；前端可重试/保持单模块。
- 结构应用：
  - 非需求阶段 409；有 active Change Set 时按 M5 规则处理（建议：规划入口禁用/提示先完成/取消变更）；
  - 已归档模块不参与；至少保留 1 个未归档模块（若规划为空则 400）；
  - 重开已确认模块需显式确认；清应用级确认/bundle 需重新确认；
  - 事务失败回滚；旧模块归档不删除。
- 生成：
  - 只生成指定模块；空/失败可重试；
  - 生成内容不得写其它模块；跨模块引用只提示；
  - 全局 ID 由后端分配；不要信任 AI ID；
  - 生成失败不影响已完成模块；模块保持 draft。
- 安全：沿用现有脱敏/密钥边界；不把真实凭据传入 prompt；不读 `.env`。

## 13. 验收 / 测试计划（建议）

### 13.1 核心验收

1. 新应用首次输入用户样例 → 建议 2 个模块：商品管理、订单管理；不出现“商品明细模块”“支付模块”。
2. 应用后：MOD-001 复用为商品管理（保留 ID/对话），新建订单管理；两模块各生成完整 PRD。
3. 商品管理文档含商品/明细 CRUD、1:1；订单管理含选商品生成订单、查询、不支付；跨模块依赖订单→商品；订单文档不重复建商品实体。
4. 两模块 draft；逐模块确认后完成需求阶段；bundle 正常。
5. 重规划“把订单拆成订单和售后” → 预览 diff；订单保留或重生成、售后新建、旧模块归档；生成新模块；覆盖/缺口可见。
6. 重规划“合并商品管理+商品明细” → 不出现独立明细模块；旧模块归档；新文档完整。
7. keep 模块不改内容/版本/对话；rename 保留 ID/对话；archive 可恢复；已确认模块重开有警告。
8. 模块数量 1/2/5 个场景；无硬上限；>8 warning。
9. 规划失败/生成失败：不写错模块；可重试/保持单模块。
10. 设计/开发阶段入口禁用/提示路径；Change Set 不受影响。

### 13.2 测试

- 后端单测（不调真实模型，注入规划/生成结果）：
  - plan JSON 解析/校验/动作映射/覆盖/未分配；
  - apply：复用默认/新建/改名/归档/重开/事务/标题；
  - generate：prompt 只含当前模块/依赖；DOC_JSON 应用/版本/失败重试；全局 ID；
  - 守卫：非需求阶段、归档、active Change Set、已确认重开。
- 前端纯逻辑：plan 编辑/排序/动作/diff/覆盖展示、进度状态机、重试/取消。
- Playwright（临时数据、mock 模型/规划/生成）：
  - 首次建议卡 → 编辑 → 应用 → 进度 → 两模块文档；
  - 保持单模块；
  - 重规划 diff → 保留/改名/新建/归档 → 生成；
  - 已确认警告/重开；
  - 失败重试/取消；响应式/深浅色；
  - 0 console/API 错误、无横向溢出。
- 真实模型 E2E（实施后主会话）：用户样例 → 2 模块 → 两份文档；耗时/质量记录；临时应用跑完删除。

## 14. 里程碑建议

- **RMP-1（首次规划 + 生成）**：`MODULE_PLAN_JSON`、首次建议卡、apply（复用默认+新建）、逐模块生成/进度/重试、默认标题处理。新应用可跑通。
- **RMP-2（随时重规划）**：AI 规划入口/弹窗、当前全部需求聚合、keep/rename/regenerate/archive/create diff、覆盖/缺口、已确认重开警告。
- **RMP-3（后续）**：手工合并/拆分编辑、规划历史、Change Set 内重规划、后台生成任务。

建议 RMP-1 与 RMP-2 分两次实施/评审；RMP-1 完成即可先用新应用验证拆分质量，再上 RMP-2。

## 15. 已确认决策（2026-11-16）

1. **内容策略**：keep/rename 保留；create/regenerate 重新生成完整 PRD；旧模块 archive 保留；不机械搬运章节/Epic。
2. **重规划范围**：需求阶段、最终“完成需求阶段”之前可用；最终确认后模块与需求锁定，设计/开发走 Change Set（含重新走需求变更）。
3. **入口**：重规划用独立“AI 规划模块”弹窗/指令框；先按此观察效果，不在模块聊天里做自然语言意图识别。
4. **已确认模块**：需求阶段内重规划时自动重开 + 明确警告 + 需再次确认。
5. **实施节奏**：先 RMP-1（首次规划 + 逐模块生成）评审通过，再做 RMP-2（随时重规划）。
6. **模块上限**：不设硬上限，>8 个给 warning 与时长提示；技术保护 50 个。
7. **Change Set 内 AI 重新规划**：不在 RMP-1/RMP-2；另行设计。现有 Change Set 模块选择/新增语义不变。
