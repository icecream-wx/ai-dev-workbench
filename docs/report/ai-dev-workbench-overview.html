前一阶段确认才进入下一阶段；设计完成时确定性生成开发交接包，开发交给 opencode 原生 agent； 需求或设计要改，就走变更单，只重开受影响的模块。本文说明业务怎么走通、门禁在哪、为什么可信。

01一页摘要

把它当成一条“从想法到可运行应用”的流水线：需求变成可确认的文档，设计变成可执行的数据与页面，交接包变成开发 agent 的唯一输入，改动则通过变更单回到对应的模块。

它解决什么问题

需求散、验收缺

模板化 PRD + 章节必填校验 + 模块内 Scene/Epic/Story；AI 建议先预览、按章节勾选应用。

大系统一份 PRD 写糊

按业务域拆模块：一个模块 = 一份完整 PRD + 一套设计（实体/页面集/原型/版本/确认）。

需求改了设计还旧

设计输入绑定需求版本 + hash，需求一变按模块判定“过期”，同步与重新确认有明确入口。

交接靠人讲

确定性生成交接包（需求/数据模型/页面/计划/变更/schema/manifest/原型图），开发只读文档即可开工。

改需求像推倒重来

变更单选择受影响模块，未选模块逐行不动；05-CHANGES.md 给出真实增量 diff。

开发过程黑盒

原生 opencode 会话时间线：工具卡、diff、shell、权限/表单、上下文健康度、会话归档与恢复。

适用与不适用

适合

中小型业务应用（EOS 后端 + Vue3 前端）、通常 1—6 个业务域、需求会反复调整、需要“评审 → 确认 → 交接 → 增量实现”可追溯链路、个人或小组快速交付。

本期不适合

强合规与审批流、多租户/大团队并发协作（无登录与角色）、要求自动验收与交付证据链、与既有需求/项目管理平台双向同步。

3.1 需求阶段

左侧 AI 对话、右侧模板化 Markdown 文档；模块是需求大纲的根节点，Epics/Stories 是模块内拆分。

  • 创建即定模板：新建应用时选需求模板与原型模板。需求阶段可选 标准 PRD（13 节）、精简 PRD（6 节）；业务策略同属需求阶段可选模板，但不直接进入设计；QA / 测试计划属测试阶段，需求阶段不可选（下拉只列需求阶段模板）。
  • 先规划再写：第一段实质需求进去，AI 先给「模块拆分建议」（名称/范围/建议 Epics/依赖/覆盖），可改名、增删、调顺序，再「应用拆分并生成」或「保持单模块」。
  • 逐模块生成：每个模块都覆盖模板全部章节；必需章节不可空；不适用处写明并说明；进度可见、失败可重试、可取消。
  • 随时重规划：用「AI 规划模块」按当前全部需求重新拆分（保留 / 改名 / 重新生成 / 新建 / 归档），先看 diff 再应用；未匹配旧模块归档，内容/版本/对话保留。
  • AI 建议先预览：不写库、不产版本 → 章节勾选 + 行级 diff → 应用选中 / 忽略。
  • 版本有来源：自动保存不产版本；手动保存、模板切换、AI 应用、确认、回滚、取消恢复才产版本。
  • 逐模块确认：必填章节非空 + 至少 1 个 Epic/Story；确认后该模块只读，其它模块可继续。
  • 完成需求阶段：全部必选模块确认后，在需求总览点击，生成需求聚合 bundle 并进入设计。
  • 参考原型（可选）：每模块「原型预览」节点，显式生成 AI 参考原型，检查字段与页面是否够用——仅需求评审。
  • 导出：导出当前模块 PRD（.md），内容即该模块需求正文。

3.2 设计阶段

左侧设计对话 + 中部设计大纲树（模块根 / 数据集 / Epic / 页面集 / 未归属）+ 右侧实体、原型、覆盖度三个 Tab。

  • 模块一一对应：每个模块有自己的设计项目、版本、确认状态；切模块前先落盘，避免丢输入。
  • 按 Epic 生成：可批量勾选或单 Epic 生成；一次产出该 Epic 所需实体 + 一个页面集，实体合并进模块共享池，不删其它 Epic 的实体/字段/关系。
  • 草稿 + 每 Epic 一个版本：生成结果不自动确认；批量有进度、失败重试、停止剩余；整模块生成作为兜底。
  • 已确认项显式重开：目标含已确认实体/页面集时，需勾选「允许重新打开已确认项」，仅受影响项退回草稿。
  • 每页 PNG 是硬条件：页面原型截图齐全才能生成交接包（不是提示，是阻塞校验）。
  • 覆盖度与过期：Story 是否落到页面（未覆盖只提示）；需求变更 → 该模块设计输入过期 → 同步后才能确认。
  • 跨模块关系：允许实体关系引用其它模块实体（只 warning）；页面集只能属于一个模块。
  • 逐模块确认设计：全部必选模块确认后，才能在交接包弹窗生成应用级交接包。

3.3 开发阶段

交接包（文档契约）+ Change Set #1（初始开发基线）+ opencode 原生 build agent 会话。

  • 交接包即入口：生成成功后应用进入开发，首条提示只指向 docs/handoff/00-README.md；会话记录交接包版本 + hash。
  • 按需分阶段：大交接包（Story ≥10 / 页面 ≥12 / 文本 ≥100KB）提示「按阶段开发」，用户点击才生成阶段；普通包不生成。
  • 两层阶段：模块阶段只是分组/里程碑（不建会话、不调摘要）；Epic 阶段才是一个会话 + 一份阶段 brief。
  • 原生体验：时间线（用户/assistant/思考/工具卡/diff/shell/错误）、权限与表单内联卡片、可停止、可追加消息。
  • 上下文可控：chip 显示上下文占用（60% 黄 / 85% 红），可一键原生压缩，时间线出现压缩提示。
  • 会话管理：按变更单分组，可切换、重命名、备注、归档（只读）、恢复；切换/归档前先尽力中断运行。
  • 阶段完成：只改阶段状态、不归档会话，尽力生成摘要（失败回退最后回复）；跳过 / 重新打开都支持。
  • 完成确认：用户点「确认完成开发」记录完成；完成后在同一会话继续发消息，应用自动回到“开发中”（变更单保持已完成，纯开发修复不进变更单；若该会话属于已完成阶段，阶段自动回到进行中）。
  • 明确不做：自定义 dev agent/skill、固定骨架、批次、证据、Git 提交推送、测试门禁、自动验收。

04阶段间交接逻辑

4.1 需求 → 设计

机制具体行为
模块确认每模块独立确认（必填章节非空 + 至少 1 个 Epic/Story），确认后只读；其它模块可继续编辑
应用级完成「完成需求阶段」要求全部必选未归档模块已确认；生成需求聚合 bundle（模块版本 + hash + 聚合 hash），应用进入设计
设计输入每个模块的设计项目绑定该模块需求版本 + hash；设计输入 v2 还记录 bundle 版本/hash
过期判定需求变化 → 该模块设计输入 stale（按模块判定，不牵连其它模块）；应用级 bundle 漂移只提示
重新同步同步弹窗可选重新绑定/仅预览/延后，并标记受影响项；历史版本不丢
回退「重新编辑需求」退回草稿；应用回需求阶段、设计暂时锁定，已生成设计/原型保留但标记过期

一句话：需求不是“写完就算”，而是“确认成快照 + 设计绑定这个快照”，所以“设计基于哪一版需求”永远说得清。

交接包文件作用

生成前校验（不过就 400 + 具体问题，不写盘、不切阶段）

  • 全部必选未归档模块的需求已确认、设计已确认；
  • 每个模块的设计输入已绑定且未过期（stale 阻塞）；
  • 引用完整：requirementRefs、epicId、storyIds 必须存在；页面绑定实体必须存在；
  • 每一页都有原型 PNG（文件存在且是 PNG）；
  • 跨模块实体关系、跨模块表名重复、模板不一致 → 只 warning，不阻塞。

生成时发生什么

  1. 预览只渲染、不写盘、不建变更单；
  2. 生成写盘 + 版本递增 + 整体/单文件 SHA-256 + 记录交接包；
  3. 首次生成创建 Change Set #1（初始开发）并写入全部未归档模块的基线行，应用状态 → 开发；
  4. 开发会话记录交接包版本 + hash + 变更单，开发页显示「交接包 vN · 初始开发」；
  5. 开发阶段且变更单仍在进行中时可重新生成：版本递增、复用同一变更单，并提示“应用目录可能已有代码，请增量修改”；变更单已完成或应用已完成后需先「发起变更」，否则生成返回 409。

说明：磁盘只保留最新版本的交接包文件；历史版本保留元数据/hash/manifest，但不再提供文件内容与图片 URL（避免指向当前版本的文件）；需要历史内容时重新生成。

4.3 开发 → 变更（Change Set #2 起）

环节行为
发起应用头部「发起变更」：选受影响模块（默认全选）+ 范围（需求+设计 / 仅设计）；「仅设计」之后可升级为「需求+设计」
重开范围只把选中模块的需求与设计退回草稿并重开确认；未选模块版本、确认、设计输入逐行不动
只读未选模块在需求/设计页整块只读（写操作 409）；部分模块变更时应用级模板切换被禁用（改为模块级）
基线变更单按模块记录需求/设计 baseline 版本与 hash；取消时按模块恢复
做变更改需求 → 逐模块重新确认 → 同步设计输入（解除过期）→ 逐模块确认设计
重新生成交接包 v(N+1)：05-CHANGES 按模块给真实 diff，未选模块写“未变更”，新模块写“新增模块”
新会话建议新建开发会话做增量实现；旧会话按变更单分组保留，可回看
取消只能在新交接包生成前取消；按模块恢复需求/设计/模板/设计输入，并在同一事务重生成需求 bundle；变更中新增模块自动归档（内容保留、可恢复）
禁止项变更中不能归档模块；未选模块的任何写操作都返回 409（只读）

一句话：变更不是“改一个字段全链路重来”，而是“选模块 → 重开这一块 → 增量 diff → 增量实现”。

4.4 两层开发阶段

维度模块阶段（module）Epic 阶段（epic）
作用分组 / 里程碑，展示模块整体进度实际执行单元
会话不建会话一个阶段一个原生会话
摘要不单独调模型，聚合展示子阶段摘要/进度完成时生成摘要（失败回退最后回复）
操作不可开始/完成/跳过/重新打开（409），只读展示可开始/完成/跳过/重新打开；完成不归档
状态由子阶段派生（有进度→进行中；全部完成/跳过→已完成）自身状态机

单模块应用保持原有平铺阶段（基础 + 每个 Epic）；多模块应用才启用“模块 + Epic”两层，避免小项目被过度结构化。

05关键机制：为什么可信

模板与章节

模板决定“问什么、写什么、确认什么”。内置 4 个模板：标准 PRD（13 节）、精简 PRD（6 节）、业务策略（需求阶段可选，但不直接进入设计）、QA / 测试计划（测试阶段，需求阶段不可选）；另有 2 个原型模板。创建时选择，之后可切换（应用级切换有逐模块影响预览与二次确认）。模板只存 id/hash，正文不进版本历史。

模块化

模块是业务域/协作边界，不按 CRUD、不按单实体拆。AI 规划建议通常 1—6 个模块：建议 >8 个时给 warning（逐模块生成耗时长），>50 个直接拒绝（MAX_PLAN_MODULES=50，仅约束 AI 规划/重规划）；手工新增模块不设硬上限。模块有独立文档、设计、版本、确认、变更范围、负责人标签，新增只在需求阶段。

版本 checkpoint

自动保存不产版本，避免版本爆炸；模板切换、AI 应用、确认、回滚、取消恢复、手动保存才产版本并带来源标签。需求与设计版本都按模块独立，可回滚（回滚本身也产版本）。

确认与只读

已确认的文档/设计只读；归档模块只读；变更范围外只读；历史会话与历史交接包只读。只读是状态机语义，不是权限系统——本期没有登录/角色。

变更单与追溯

每次变更是 Change Set（#1 初始开发，#2 起真实变更），记录范围、模块基线、状态、时间。05-CHANGES + manifest 让 agent 明确“这次只改什么”；交接包、会话、阶段都绑定变更单与包版本。

交接包确定性

完全由结构化数据渲染，导出时不调模型；同一份数据多次生成内容一致（除版本/时间戳）。文档不用内部 ID，按模块稳定编号（ENT-001 / PS-001 / PAGE-001）。

规模识别

Story ≥10 / 页面 ≥12 / 文本 ≥100KB → 写入 manifest.scale，04-PLAN 插入“建议分阶段（可选）”，弹窗与开发页显示规模与入口；不强制、不门禁。

原生 opencode

用原生 build agent、原生会话/SSE/权限/表单/取消/compact。工作台只提供目录、会话 UI、转发与完成确认；不做自定义 agent、批次、证据、Git 门禁。

AI 参考原型边界

由需求 agent 从 PRD 生成预览规格，用设计阶段同一渲染器 + 示例数据展示真实字段。只写一个设置键：不写业务表、不产 PNG、不进设计/交接包；界面标注“仅用于需求评审”，需求变更提示重新生成。

失败重试与容错

模型输出按协议分隔符解析且互不复用；原型规格解析容忍围栏/BOM/尾逗号/全角引号/裸换行，失败自动重试一次，仍失败给 502 + 可展开诊断片段且不覆盖旧规格。生成类操作“成功才写库/写盘”。

6.3 十分钟演示（加深度）

在 3 分钟版基础上补 4 段：

  1. 模块规划：输入一段业务描述 → 建议卡出现 2 个模块 → 改名/调顺序 → 「应用拆分并生成」→ 看逐模块进度与两份文档。讲：模块数由内容决定，确认前不写库。
  2. 版本与确认：打开版本弹窗，指出“自动保存不产版本”，再指出确认/模板切换/AI 应用产版本且带来源；点「确认需求」看只读横幅与「重新编辑需求」。
  3. 过期与同步：改需求后回设计页，看“需求已更新”提示与同步入口；讲“设计绑定需求版本 + hash”。
  4. 变更闭环：发起变更（只选一个模块）→ 改需求 → 确认 → 同步 → 确认设计 → 生成 v2 交接包 → 打开 05-CHANGES.md 看 diff（另一模块标“未变更”）→ 新会话增量实现；再演示「取消变更」恢复基线。

6.4 演示注意事项

  • 真实模型有耗时与波动：单模块需求约 30—60 秒、设计实体/页面集约 15—35 秒（2026-11-16 实测）；重要演示前先试跑。
  • 界面信息量与数据准备相关：优先演示已确认模块、已生成的交接包与已有会话。
  • 不要填写真实 DB / Nacos / 邮件凭据：这些字段只用于渲染应用目录中的配置文件，未填写即写 CHANGE_ME。
